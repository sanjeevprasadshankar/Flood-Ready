Prediction Approach
Method: Weighted multi-signal risk score (rule-based, no black box)
Features used:
  • River Level % of Danger (40 pts) — proximity to danger threshold
  • River Rise Rate 1-day (20 pts) — how fast the river is rising
  • Upstream Level Rise (20 pts) — leading indicator (~1 day lag)
  • 3-day Cumulative Rainfall (10 pts) — sustained moisture input
  • Soil Moisture % (10 pts) — saturation reduces absorption

Threshold: Score ≥ 45 → Flood Predicted
Split: Train Jul 1–Aug 9 | Test Aug 10–29
Key insight: Recall (86%) is prioritised over Precision (35%) because a missed flood costs lives; false alarms can be filtered by the duty officer.

Village Prioritisation Formula
Combined Score = 0.60 × Risk Score + 0.40 × Priority Score

Priority Score is built from:
  • Population + 2× Vulnerable (max 35 pts) — who needs help
  • Shelter capacity gap (max 25 pts) — whether shelter can absorb everyone
  • Road access: Cut off = 30 pts, Seasonal = 15 pts, All-weather = 0 pts
  • Phone coverage gap (max 10 pts) — alertability

This ensures cut-off villages with high vulnerable populations rise to the top even if the raw flood risk is equal.
🏗️ System Architecture — Production Design
📥 Ingest & Store
📡
IoT Gauge Sensors
RS-485 / LoRaWAN sensors push readings every 15 min to MQTT broker
🌧️
Rainfall API Feed
IMD / OpenWeather ingested hourly via REST; upstream level from API
🗄️
Time-Series DB
InfluxDB for sensor streams; PostgreSQL for village & shelter registry
🔄
Data Quality Pipeline
Apache Airflow DAG: outlier clamp, interpolation, duplicate drop — runs every 30 min
⚙️ Process & Predict
🧮
Feature Engine
Computes rolling stats (3-day rain, rise rate, upstream lag) on each new reading batch
🤖
Risk Scoring Model
Weighted rule model (explainable, auditable). Retrained monthly with new labelled data. Runs every 30 min
🗺️
Village Prioritiser
Joins gauge risk with village vulnerability index; outputs ranked list per alert trigger
📊
Alert Engine
Generates plain-language alerts in 3 languages; selects delivery channel per village preference
📤 Deliver & Oversee
👮
Officer Dashboard
District officer reviews ranked alert list before any alert is dispatched (human-in-the-loop gate)
📱
SMS / WhatsApp
Twilio / Gupshup gateway; phone-coverage fallback routes to loudspeaker coordinator
📢
Loudspeaker Network
Panchayat coordinator receives WhatsApp + voice call to activate village PA system
🔒
Security & Privacy
Village vulnerability data: role-based access, AES-256 at rest, TLS in transit. Officers only see aggregates
Scalability & Reliability
⚡
Scale to 600 Gauges
Horizontally scalable MQTT broker (EMQX) + InfluxDB cluster. Alert engine runs as stateless Lambda-style workers.
📴
Sensor Failure Fallback
If a reading is missing for >2h, dashboard shows ⚠️ SENSOR OFFLINE. Last known value shown with staleness flag. Officer is paged.
🔋
Network Outage
Edge nodes store 24h of readings locally; sync when connectivity restores. SMS alerts use low-bandwidth USSD fallback.
⚖️ Responsible AI Commitments
🎯
Missed Floods vs False Alarms
We set our threshold at 45 (not 60+) to maximise recall (86%). A missed flood can cost lives; a false alarm causes inconvenience. We accept ~3 false alarms per true flood on the test set. The duty officer reviews every alert before dispatch — their judgment is the final filter. Alert fatigue is mitigated by explaining each trigger in plain language.
🤝
Equity of Reach
Our priority formula explicitly rewards villages with high phone-less household rates and cut-off roads. A village of 720 with 52% no-phone access and flooded roads scores higher than a larger village with all-weather roads and full phone coverage. Loudspeaker deployment is flagged as mandatory for any village above 40% no-phone threshold.
🔒
Data Privacy
Village vulnerability data (population breakdowns, shelter capacity) is sensitive. Access is role-gated: field officers see only their assigned villages; district officers see aggregated metrics. Data is encrypted at rest (AES-256) and in transit (TLS 1.3). No personal/household-level data is stored — only village aggregates.
👮
Human Oversight & Fallback
No alert is dispatched without officer approval — the system recommends, humans decide. If the data feed fails for >2h, the dashboard shows a SENSOR OFFLINE banner and pages the on-call officer. If the model output looks anomalous (score >90 with no rainfall), a "Review Recommended" flag is shown. Manual override is always available.
📖
Explainability
Every risk score is decomposed into its five components (level %, rise rate, upstream, rainfall, soil). Every village priority score shows the three dominant factors. Officers can trace exactly why a village is ranked first — no opaque black box. This builds trust and supports accountability.
🔄
Model Drift & Feedback
Ground-truth flood labels are collected after each event. The model is re-evaluated monthly. If recall drops below 80%, thresholds are adjusted and officers are notified. Community feedback (did the alert arrive in time? was it in the right language?) is collected after each event to improve the delivery pipeline.
